# Original-object baseline

Curated name and boundary claims belong in [evidence.tsv](evidence.tsv), using the [evidence format](../README.md). The table does not apply symbols or splits to this baseline.

`baseline.json` records the DOL's section addresses, entry point, complete size, and hash. Section names are toolkit placeholders, not recovered original names or compilation-unit boundaries. The small-data bases are loaded into r13 and r2 at `0x80003108`–`0x80003114` in the target entry code.

The baseline splits the original executable into relocatable objects, links them with GNU binutils, converts the ELF back to DOL, and compares every output byte with the verified target. This demonstrates a working original-object relink, not the original compiler or linker identity, recovered source, or matching progress.

The provisional working compiler is ProDG 3.9.3, with Wibo 1.0.3 on the supported hosts. Downloads are verified against `tools/compiler-tools.json`. The isolated-stage wrapper produces native-driver-equivalent C/C++ objects, validates arguments and fresh outputs, normalizes dependency line endings, and stops the process group on timeout. It never retries with different flags or modifies compiled instructions. Compiler stages currently support POSIX hosts; macOS uses the x86-64 Wibo executable through the host's existing Rosetta support.

CI also checks ngcld's original-object relink against the complete target. A 48-byte diagnostic source reproduction is compatible with all five available ProDG versions and multiple optimization settings; it rejects `-G0` for that case. This establishes a usable toolchain, not a unique original compiler version or project-wide flag profile. Reconstructed units still need evidence for their compiler settings and source boundaries before entering the combined build.

The baseline uses `quick_analysis`; relocation processing and the complete executable comparison still run. Function boundaries and source compilation must be established separately before using CI to accept reconstructed code. Generated objects, assembly, symbols, and binaries stay under ignored `build/`.

## Function analysis

Function inference supplies provisional candidates rather than recovered source boundaries. CI runs the analysis with additional memory headroom; locally, use the command below with the verified target.

Run `python3 tools/analyze.py --original /path/to/main.dol` to generate a provisional inventory and verify its complete original-object relink with the pinned tools. Each run starts from the small seed set in `analysis.json`, rather than reusing a previous inferred inventory. Results and logs stay in `build/analysis/`.

[SDK ownership](sdk.json) partitions the identified Nintendo library ranges by candidate source file. `tools/sdk_map.py` checks the target hash, section bounds, overlaps, and coverage. `analyze.py` uses those ranges to emit separate original objects and private SDK assembly under `build/analysis/split/asm/`, then relinks and compares the entire executable. It retains unmapped bytes and validates object ordering against the original section geometry. Reviewed data extents constrain inferred object sizes where typed target evidence supports them. Separated extents of one file become private fragment objects, while the public map keeps one logical file owner. Neutral byte fragments preserve unassigned data and alignment gaps. These splits do not change source compiler settings or earn source credit. File names and original boundaries remain provisional, and unsupported data ownership stays unassigned.

Three constant/string ranges in `.text` are annotated as data. Function inference and inferred relocations are disabled only within those ranges; every byte remains linked and compared. A separate loop routine is seeded so exception code branching to it does not acquire an oversized function extent. The [evidence table](evidence.tsv) records these annotations and unresolved thunk edges.

For the analyzed relink, ngcld requires small-data output section names. Absolute references `lbl_803ED681` and the toolkit's `_stack_end` resolve to `0x803ED681`, the target value loaded at `0x8000315C`–`0x80003160`; this is not a recovered stack-symbol name. The script does not substitute a generated SDK stack formula.

An identical analyzed relink validates the mechanics, not the inventory's names, total function count, source units, or reconstructed source. Toolkit signatures and assembly boundary guesses still require review. In particular, the twelve branch/return pairs at `0x801AC9A0`–`0x801AC9FC` retain unresolved ownership of their unreachable returns; no source split is made there.

## Source build

`tools/source_build.py` compiles each unit in [units.json](units.json) with the pinned ProDG wrapper, links the objects in place of exactly their configured address ranges with ngcld through Wibo, converts the ELF with the pinned dtk, and compares every output byte with the verified target. Every other byte comes verbatim from the verified original executable as a generated raw object without relocations, so the original data's pointers need no reanalysis. With no units, the build is the complete original image and must still match.

The manifest records:

- `profiles`: named compiler flag sets, each with an `evidence` locator. Units name a profile; per-unit or per-function flags are not accepted. Each unit compiles once; there is no retry.
- An optional profile `source_root` (`directory`, `file_prefix`, `evidence`) compiles the library the way the original build did. For example, `{"directory": "src", "file_prefix": "../../../Source"}` compiles `src/Common/UIStudio/UISEvent.c` as `../../../Source/Common/UIStudio/UISEvent.c`. The compile runs from a generated directory three levels below a staging directory, whose `Source` is a symlink to the repository's `src/`. `__FILE__` then expands to the original relative spelling. The evidence for this convention is the target strings at `0x802B1DC4` and `0x802B1DF0` (`../../../Source/Common/UIStudio/…`; see the `unit-anchor` rows in [evidence.tsv](evidence.tsv)). Dependencies are resolved through the link, so the report still names repository files. Include directories are passed as absolute paths.
- `units`: a repository-relative `source`, its `profile`, an `evidence` locator for the boundaries, and one entry per compiled section: compiler `section` (`.text`, `.rodata`, `.sdata`, `.bss`, ...), placeholder `placement`, and exclusive `start`/`end` addresses. For example, a unit's `.rodata` may be placed in `.data3`. Every non-empty allocated compiled section must be configured, its size must equal its range, its alignment must fit the start address, code must go to a code section and uninitialized data to an uninitialized section. Ranges must lie inside one placeholder section and must not overlap.
- Data inside a code section: a section entry may add `follows` with the name of the unit's own code section (for example `{"section": ".rodata", "placement": ".text", ..., "follows": ".text"}`), for a unit whose read-only data the target holds directly after its code. The tool does not restrict this to an address window; it enforces the following. `follows` is the only way to place a non-executable section in a code section. The compiled section must be initialized, read-only and not executable; writable or uninitialized data is rejected. The followed entry must be an executable section of the same unit in the same placement, ending before the data with no other configured range in between. The data must start exactly at the first boundary of its own compiled alignment after the code ends, and the padding between them must be zero in the target. No original-byte piece covers that padding; ngcld produces it from the section alignment, and the complete-output comparison checks it. The data range must equal, start and end, a `data` row in [evidence.tsv](evidence.tsv) whose two edges are `exact`, and must not overlap any bounded `function` extent there; the source build and the progress exporter both check this. The progress exporter also rejects a data range that overlaps any candidate in the function inventory. Instruction bytes therefore cannot be claimed as data, even where the inventory has a gap. Constant blocks the inventory still treats as function candidates need that inventory corrected first. The data range counts toward its containing code section, like the original constant blocks in `.text`, and contains no compiled function. The report records `follows`, and the progress exporter requires it to equal the manifest.
- `externals`: curated non-neutral names with an address and evidence. Undefined references named `fn_XXXXXXXX` or `lbl_XXXXXXXX` (uppercase hexadecimal) resolve to that address without claiming a name. C++ sources must declare such labels `extern "C"`. Any other undefined symbol fails the build.

Resolved externals are defined at their offsets inside the original-byte object containing the address, which lets ngcld apply small-data relocations; `.data5` and `.data6` use the small-data section names from [analysis.json](analysis.json). A reference into another unit's configured range must name that unit's own symbol. Unit symbols may not duplicate externals, linker symbols, or another unit's definitions; a neutral label must be placed at its own address, and every defined unit symbol is checked at its final address in the linked ELF. Common symbols, unconfigured sections, size or alignment differences, linker diagnostics, and any output difference fail the build.

Hardware registers outside the executable are not externals. Under ProDG, `AT_ADDRESS` in [types.h](../../include/dolphin/types.h) is SN's `__attribute__((address(addr)))`, the counterpart of CodeWarrior's `: addr`. The compiler accepts it only on a non-extern declaration, resolves the address itself and emits a local absolute symbol with no relocation. The GX write-gather pipe `GXWGFifo` (0xCC008000, [GXVert.h](../../include/dolphin/gx/GXVert.h)) uses this form; see its `source-form` row in [evidence.tsv](evidence.tsv).

The report, `build/source/report.json`, records each unit's source and dependency hashes, profile and flags, and each section's configured range, compiled size, linked bytes and status. It also records the resolved externals and the linked/matched code and data totals. Bytes count as matched only when the complete output is identical; a failed comparison still writes the report with `complete: mismatch`, zero matched bytes, and per-range diagnostics. Uninitialized ranges have no bytes to compare; they count when their size and symbol placement check out and the complete output is identical.

dtk 1.8.4 quick analysis was evaluated for cutting original sections. With unit ranges in `splits.txt`, it stops because the inferred extents of relocation targets cross unit edges. It succeeds only after synthesized boundary symbols are added, and then it emits relocations whose targets may lie inside replaced ranges. GNU ld relinks the zero-unit image but rejects ProDG objects (`.symtab local symbol at index >= sh_info`), so source builds use ngcld only.

## Public progress

Successful builds of `main` publish the progress page. The file map uses provisional SDK ownership from `sdk.json` and measured source ranges elsewhere. Unassigned intervals stay visible. Mapping alone contributes zero linked or matched bytes; a mapped file is not reported as a complete original unit. Code totals use executable section sizes; data totals include loaded data and uninitialized memory, with overlapping loaded ranges excluded from BSS. Linked and matched measure source-object bytes from the source-build report, attributed to the executable sections that contain them; original bytes contribute zero. The report records SHA-256 hashes of the build inputs it trusts: `source_build.py`, `prodg_cc.py`, `setup_compiler.py`, `baseline.py`, both tool locks, `baseline.json` and `analysis.json`. The exporter rejects a report whose tooling hashes differ, whose unit ranges are not exactly the manifest's configured sections, or whose ranges overlap. It also rejects a report for another target or unit manifest, a report without an identical complete output, stale source or dependency hashes, and files under `src/` that are neither unit sources nor recorded dependencies. Configured units or source files without a report also stop the export. With no units, it reports zero.

### Nintendo SDK reuse

SDK imports retain the provenance in [CREDITS.md](../../CREDITS.md) and target ownership evidence in `evidence.tsv`. The public source build selects a reviewed library compiler profile: ProDG for the existing EA unit and CodeWarrior GC/1.2.5n for the imported Nintendo units. Both compilers come from the same pinned archive and use the same pinned Wibo; supporting build dependencies remain unchanged. The SDK path preserves native compiler objects, tracks source/header dependencies, and uses the existing complete-target comparison and measured progress checks.

To screen existing compiled SDK objects for reuse, write the candidate inventory to local research:

```sh
python3 tools/sdk_scan.py --original /path/to/main.dol --object-root /path/to/compiled/sdk --output scratch/sdk/candidates.json
```

The scanner masks only recognized relocation fields and distinguishes unique, ambiguous and absent fingerprints. A unique hit requires inspection of calls, globals, used types, data ownership and original unit boundaries before import. Short functions below 32 bytes need separate evidence. An absent hit can reflect dead stripping or a different SDK version. Candidate output is private research and never supplies progress. Matching SDK code still receives the accuracy and hostile-review passes; unsupported matching tricks in a reference remain excluded.

SDK units with `link_roots` support retained code and static data. Static section sizes, symbol identities and offsets must remain consistent with native compiler output; SN-generated BSS metadata is excluded from source ownership. The roots identify target-retained entry points; SN’s original linker retains their dependencies and discards unused library functions. A relocatable partial link determines placement using temporary SDA anchors chosen for SN’s range checks; those inspection addresses do not supply target addresses or progress. The final link consumes untouched native objects with target SDA bases. Retention is a linker operation, not a function-specific compiler setting. Source, headers, roots and tools are bound to the full-build report; no progress is accepted until the complete target matches.

The same `link_roots` mechanism applies to a ProDG game unit when the target shows that SN discarded one of its functions: the function's code is absent while its static data, such as its constant pool, remains at its native offset. The unit lists every retained function as a root, because calls from original-byte objects carry no relocations. Unlike an SDK unit, it must also list every discarded function in `link_roots.discarded`. The build checks that the compiler's functions minus those the linker retains are exactly that list, so no function can disappear without being declared, and a declared function cannot stay in the output. The same retention checks as for SDK units also apply: every retained function keeps its native size, and every static section keeps its native size and symbol offsets. The manifest list is not tied to the evidence table by the build; by convention an evidence row records each discarded function's surviving data and why its code is absent. A discarded function has no target address, so it gets no function row and no function credit; its source name is descriptive. The first such unit is `src/game/cu_80026BB0.cpp` (linker row 0x80289FC8-0x80289FE0 in [evidence.tsv](evidence.tsv)).

### Independent exact and fuzzy comparisons

`tools/matching.py --original /path/to/main.dol` produces private measurements in `build/matching/report.json` using checksum-pinned objdiff 3.8.2. Pass `--comparison-report build/matching/report.json` to both progress exporters and `check_progress_maps.py`. CI performs this measurement before publishing either report.

The bars layer verified **linked** source bytes over **exact matched** bytes over **fuzzy** similarity. Exact credit requires byte equality; fuzzy credit weights objdiff similarity by byte size. Mapping and original-byte objects receive neither kind of match credit. Fuzzy similarity is a diagnostic, not evidence of faithful source reconstruction or a completed unit.

[comparisons.json](comparisons.json), schema 2, registers partial functions in their normal `src/` files. These entries and reviewed source may be committed and merged while mismatches remain; CI publishes their measured progress independently of linked-source credit. Each entry names `source`, the existing file-wide `profile`, boundary `evidence`, target `sections` (the same placement format as units.json), and `functions` (`symbol`, target `start`, target `end`). Target function edges and initialized data extents must be evidenced; registered ranges cannot overlap. A file with linked and draft functions usually compiles one data section that spans both. Register that section's full native target placement: draft code relocates against it unchanged. Only the slices outside the file's linked placements are measured. Each slice must exactly equal an evidence.tsv `data` row with exact edges; the schema has no slice field. Every placement byte must be either an evidenced slice or linked source of the same file. Linked bytes of another file, or a linked placement extending past the registration, fail validation. A sliced placement must compile to the full target size and reproduce its linked bytes at their native offsets. Receipt reload recomputes the slices from the verified source-build report and rejects a missing slice, duplicate credit, or credit for any linked byte. Functions remain whole: a registered function partly inside linked source fails. The profile must be the same as the accepted source's profile when a file has both linked and draft functions. Empty registration means there is no additional unfinished-source progress; it is not an estimate of unpublished work.

For a file that already contributes linked source, put draft bodies behind the fixed global comparison-build guard:

```c
#if defined(DECOMP_COMPARE)
/* Draft bodies remain in this file alongside accepted source. */
int fn_XXXXXXXX(int value) {
    /* Evidence-supported reconstruction in progress. */
    return value;
}
#endif
```

The example is a workflow illustration, not game source or matching evidence. The accepted build never defines `DECOMP_COMPARE`; its original-byte objects continue to supply the unlinked ranges. The comparison build defines it globally for both supported compilers and uses the same file-wide compiler profile and include/source-root convention. It is a body-selection mode, not alternate optimization settings. Profiles cannot override this reserved mode. A wholly unlinked source file need not guard its bodies, since it is absent from units.json. Headers stay in the normal include tree. Register source in comparisons.json rather than moving it to another folder.

Diagnostic fragments retain unchanged native function/data bytes and their relocation records; only ELF symbol/offset metadata is rebased for isolated linking. The original compiler object is never modified or substituted in the accepted build. Same-file calls resolve through explicit target function identities, and data references use configured target section placements; unknown identities fail closed. Diagnostic links use target SDA bases and evidenced external addresses. Each registered function is positioned at its target address before comparing its complete compiler-produced body; compiled and target sizes may differ. Scores are weighted by **target** size, never by an expanded draft body. Unresolved symbols, missing functions, overlapping target spans, unconfigured allocated sections and stale receipts fail export. Linked ranges are not credited twice when comparison source also contains accepted functions. Uninitialized storage earns no speculative fuzzy credit. Data configured to follow code inside a code section is not supported for draft comparisons yet; accepted source retains its existing support. Diagnostic initialized-data fragments with relocations into their own small-data section are also unsupported and fail closed.

Function status comes from measurements: unequal bytes yield fuzzy similarity; equal complete bytes yield exact matched credit; only ranges in the byte-identical accepted source build yield linked credit. An exact draft remains unlinked until its original assembly replacement passes review and the full build. Remove its guard, add or expand its accepted placement in units.json, and record attribution when promoting it. Keep the source path unchanged. Remove obsolete comparison registration when all its ranges are linked. Do not withhold reviewed partial source solely because it is not ready for promotion. Discarded experiments remain private; useful partial reconstruction remains in the repository with measured comparisons and documented unknowns.

Both exporters consume the same verified comparison receipt. decomp.dev uses `fuzzy_match_percent` for its **code** bar, so our report and unit scalars intentionally use a code-only denominator. Data similarity is retained in `units[].sections[]`; its current data bar supports linked and exact progress only. Our page separately displays code and data fuzzy progress. Completed-unit flags/counts require exact source-unit boundary evidence as well as every mapped code/data extent being linked. Partial/provisional files remain incomplete, even when their represented functions are green at 100% similarity. Unmapped bytes never become completed units.

Comparisons use resolved function bytes and explicit data spans wrapped in private relocatable objects for objdiff. This is a bounded resolved-byte comparison, rather than a reconstruction of original object relocations. Uninitialized storage has no fuzzy byte score; verified linked storage retains its existing exact credit. Measurements bind the target, tool versions, configuration, compiler receipt, source and dependency hashes, and full extent coverage. Raw objects, binaries and trial output remain under ignored `build/`.

### Timeline and contributor credits

`tools/activity.py` exports `build/site/activity.json` after the verified progress exports. The graph shows linked code/data bytes divided by their respective executable totals. [history.json](history.json) seeds it with 62 successful `main` build artifacts, recording the revision, timestamp, workflow run, artifact ID, and downloaded report hash. Original bytes and provisional ownership earn no progress. The initial history has consistent code/data denominators; missing older builds are not estimated.

On a `main` publication, CI restores history from the artifact attached to the last successful Pages deployment and appends the verified current measurement. It merges by revision, preserves the first successful timestamp, rejects conflicting measurements, validates the target and Git ancestry, and refuses to reset history if an artifact is missing, expired or inconsistent with its deployment. Bootstrap without an activity file is allowed only for the audited pre-feature revisions in the seed. A stale CDN response is never used for history storage. PR previews retain merged history without recording their branch as a published milestone. The checkout includes full Git history for these checks; the workflow adds only repository Actions read permission to retrieve artifacts; no write token or repository write permission is added.

[contributors.json](contributors.json) records credited compiled-function addresses by source, GitHub identity, original contribution PR, merged integration PR, and introduced source commit/blob. Batch imports preserve original PR authors. The retroactive audit compared original source blobs with their integrated versions; documented declaration/type/symbol adjustments preserve original contribution credit. Dependent PRs carrying an earlier source file are not extra contributions. SDK credit here describes the contributor who integrated the verified source, not original Nintendo authorship; library provenance remains in CREDITS.md.

For new or newly retained compiled functions, add their addresses and contributor identity to this ledger as part of the contribution. Credit follows the original source contribution, not the author of a combined PR. An explicit multi-contributor entry credits each person once; integration/review alone does not transfer function credit. Export rejects missing or duplicate attribution and unexplained integration changes. It verifies the pinned original commit/source blob independently from the introduced blob at that source path in reachable revision history, so squash integration preserves original authorship. Adjusted imports also record the original commit. Missing commit objects fail validation; CI explicitly fetches only pinned provenance commits from this checkout’s origin on the host before exporting. Retired functions remain in the ledger for provenance but disappear from current counts. Addresses identify compiler-reported retained functions; these counts are distinct from the evidence-gated exact-function statistic. Review the attribution with the source PR and preserve it when batching. The page sorts by current distinct credited functions, with login as the deterministic tie-breaker.

To bootstrap a new contribution, complete the local source build and independent source reviews, then open a draft PR to obtain its real number. Add the ledger entry with that contribution PR number (`merged_via` initially the same number), and complete final activity/export validation before marking it ready. A batch replaces `merged_via` with its actual draft PR number; it does not change original attribution. Do not guess future PR numbers or use issue numbers as contribution PRs.

Before marking an integration ready, validate its complete ledger after a synthetic squash onto the actual PR base (`tools/activity.py --squash-base BASE_SHA` with verified exports). PR CI performs this check using GitHub’s PR base SHA. An introduced blob must be retained in that resulting source history; an older version visible only on a contribution branch is insufficient. Preserve that earlier original commit/blob separately when a reviewed correction changes the imported source.

The public **Files exact** and **Files named** cards count distinct mapped file identities, combining their code and data entries. The denominator is the current mapped-file inventory, not an estimate of all original files. Named includes descriptive inferred names as well as recovered names; address-based boilerplate labels receive no named credit. Exact requires confirmed whole-unit code boundaries and every mapped code/data extent matched, including exact unlinked comparisons. Completed-unit linking remains a separate measure.
